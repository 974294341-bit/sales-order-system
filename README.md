# 销售订货全流程协同系统 · 实战项目复盘

> 一个用 **纯 JDK 25（零第三方依赖）** 实现的销售订货管理系统：覆盖接单、库存判断、订单评审、变更、急插单、联络单、预测、交付率、周期表等 10 项业务域，配套 **PC 工作台 + 手机端审批**，内置 JWT+RBAC 权限、集中式状态机、流程引擎、SLA 超时升级，前端用原生 HTML/CSS/JS + 纯 SVG 图表。

---

## 一、项目背景与动机

这是我在 Java 后端方向上做的一个**完整业务系统实战项目**。选题来自一套非常典型的制造业场景：

> 一家中小型装备制造企业，销售订货流程长期靠 Excel + 微信群流转。业务接单后，库存是否够、要不要评审、谁该签字、变更怎么留痕、急单怎么插、联络单怎么闭环，全靠人肉盯。结果就是：职责边界模糊、评审串行拖沓、库存判断错位、变更无版本、急插单失控、单据搁置无人知。

客户（这里指业务侧提出的真实诉求）希望有一套系统把这条链路数字化、规范化。我把它拆成 **10 项核心业务需求**，并在这个项目里逐一落地。

**为什么选择"零依赖、纯 JDK"的实现路线？**
- 项目要能在任意装了 JDK 的机器上 `javac` 即编、`java` 即跑，不依赖 Maven 私服或外网下载；
- 把复杂度收敛到**自己写的平台层**（JSON、路由、鉴权、存储、状态机、流程引擎），反而更利于讲清楚"一个业务系统到底由哪些零件组成"；
- 后端只用 JDK 内置的 `jdk.httpserver` + 标准库，前端零构建步骤，整体可移植性极强。

## 二、客户需求拆解（10 项核心业务需求）

我把业务侧诉求归纳为下面 10 条，每条都对应一个可演示、可验收的功能模块：

| 编号 | 客户需求 | 业务含义 | 系统落地 |
| -- | ----------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| R1 | **接单与智能库存判断** | 业务录单时，系统要先判断库存是否齐备：齐备直接走发货，不齐备才进入评审，避免"先评审再看库存"的无效流转 | 库存优先短路：`STOCK_DIRECT` 直发 vs 进入 `IN_REVIEW` |
| R2 | **订单内容强规范** | 样品鉴定、试产、BOM、生产周期表等必填与一致性必须被系统卡住，不能靠人提醒 | `BusinessRules.assertOrderBasics` 统一校验，覆盖预测订单 |
| R3 | **多角色协同评审** | 一张订单要财务、工程、计划等多岗参与；财务必须前置；标准品与非标品走不同分支；能并行会签就别串行 | 财务前置 + 标准/非标分支 + 并行会签（`FlowEngine`） |
| R4 | **订单变更闭环** | 变更要按类型分派会签、保留前后版本快照、确认成本影响、回写 ERP | `ChangeService` 三类型分派 + 版本历史 + 金额同步 |
| R5 | **急插单管控** | 急单不能想插就插：要有提前期、产能校验、月度上限、且客户同意顺延 | 月度上限 + 前置任务 + 书面通知，驳回即取消 |
| R6 | **生产入库与发货联动** | 完工入库自动增库存，按最新约定交期发货自动扣库存，库存账实一致 | `DeliveryService` 入库/出库回写库存 |
| R7 | **联络单闭环** | 不是订单、但又要处理的需求（如客户咨询、售后）要有独立四态闭环 | 待审批 → 待计划处理 → 待业务确认 → 已结案 |
| R8 | **预测需求计划** | 月度销售预测要能转成"预测销售订单"进入生产统筹，但不能跳过基础校验 | PMC 录入预测 → `advanceForecast` 统一责任人 |
| R9 | **准时交付率考核** | 每月统计准时交付率，按正常/急插/预测分组，并触发改善措施 | `StatsService.report`，以最新约定交期为基准 |
| R10 | **产品生产周期表受控** | 周期表半年更新一次，需领导审批、文控受控发行，作为评审刚性约束 | 审批流 + 受控状态，被新建/变更/延期共用 |

### 我帮客户兜住的 14 个"隐性坑"

需求文档往往只写"要做什么"，真正难的在边界与异常。下面这些是我落地时主动补上的工程决策（也是这个系统有别于"玩具 CRUD"的地方）：

| # | 客户没明说、但必须解决的隐性问题 | 落地方案 |
| -- | ------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 1 | 权责边界模糊、预测岗位冲突、财务不参与评审 | 权责表 + 财务前置 + 预测统一责任人 |
| 2 | 采购/品质职责缺失 | 新增角色，非标产品四部门并行会签 |
| 3 | 评审全串行效率低 | 标准并行、非标 BOM 定稿后并行，会签全完成才推进 |
| 4 | 预测订单跳过全部校验 | 预测也走 `assertOrderBasics`（样品/试产/BOM/周期表） |
| 5 | 库存判断放在评审之后（本末倒置） | 接单即判库存，齐备直接发货 |
| 6 | 急插单无产能/上限/客户不同意分支 | 月度上限 + 两条前置任务 + 书面通知 |
| 7 | 变更不分类型、无版本、无成本确认 | 三类分派 + 版本前后快照 + 金额同步 |
| 8 | 联络单无闭环 | 四态状态机闭环归档 |
| 9 | 周期表只约束新建订单 | 被新建/变更/延期共用，覆盖预测 |
| 10 | BOM 时限口径模糊、可无限顺延 | 按任务接收日计数，最多顺延 3 天 |
| 11 | 准时交付口径缺失 | 以最新约定交期为基准，分组统计 |
| 12 | 没有状态机，状态随便跳 | 集中式 `StateMachine` 校验所有跳转，PC/手机端共用 |
| 13 | 手机端权限笼统 | `X-Client: mobile` 只能查看+审批；审批字段白名单 |
| 14 | 人员离职/单据搁置无告警 | `SlaService` 全节点逾期扫描、幂等升级给部门主管 |

## 三、技术选型

| 维度 | 选择 | 理由 |
| ---- | ---- | ---- |
| 语言 | Java 25（JDK 内置 `jdk.httpserver`） | 零第三方依赖，`javac` 即编、`java` 即跑 |
| 后端架构 | 分层：platform（基础设施）+ modules（业务） | 关注点分离，平台层可复用 |
| 鉴权 | 自实现 HS256 JWT + 刷新令牌 + RBAC | 无 Spring 依赖，逻辑透明 |
| 存储 | 单机 JSON 文件，原子替换 + 版本迁移（schema v3） | 演示零配置；仓储层隔离，可平滑换 JPA |
| 前端 | 原生 HTML/CSS/JS，令牌内存存储、401 自动刷新、5xx 重试 | 零构建；图表用纯 SVG，无图表库 |
| 权限模型 | 11 个岗位角色，按角色分派模块与待办 | 禅道式"我的地盘"分工 |

## 四、架构与核心设计

```
sales-order-system/
├─ run.bat / run.sh              # 一键编译 + 启动
├─ .env.example                  # 环境变量示例
├─ src/main/java/com/salesorder/
│  ├─ App.java                   # 装配、启动、优雅停机
│  ├─ platform/                  # Config / Json / Errors / Log / Router
│  │                             #   / HttpCtx / Resp / Ids / Store / Security
│  └─ modules/                   # FlowEngine / StateMachine / BusinessRules
│                                #   / 各 Service / Controller / SlaService / SeedData
├─ web/                          # index.html + app.js + views.js + style.css（PC）
│                                #   m.html + m.js（手机端） + api.js + charts.js
├─ scripts/smoke_test.py         # 50 项端到端冒烟
└─ docs/client/                  # 客户交付文档（功能模块与业务框架说明书）
```

**四个"系统级"零件，是这套业务能跑顺的关键：**

- **`StateMachine`（状态机）**：把订单/审批/联络单所有合法跳转收敛到一处集中校验，PC 端与手机端共用，杜绝"状态随便跳"的脏数据。
- **`FlowEngine`（流程引擎）**：同一份 `approvals` 表驱动所有审批任务，PC 与手机端进度一致；支持财务前置、标准/非标分支、并行会签、急插单前置。
- **`BusinessRules`（业务规则）**：库存判断、周期表校验、订单基础校验等被多场景复用（新建/变更/延期/预测），避免规则散落。
- **`SlaService`（超时升级）**：全节点逾期扫描，幂等地把超时单据升级给部门主管，解决"单据搁置无人知"。

## 五、界面与体验

- **PC 工作台**：禅道式深蓝顶栏 + 按岗位分组的左侧导航 + "我的地盘"待办 + 表格化单据 + 流程进度；配色与密度参考畅捷通浅色企业风。切换岗位后只显示该岗位能操作的模块与待办。
- **手机端审批**：登录后"我的"页看经营概览 + 待我审批列表，点开单据可同意/驳回/转交，与 PC 端共用同一份审批任务。
- **数据看板**：纯 SVG 零依赖绘制环形图、仪表盘、横向条形、面积折线，展示订单状态分布、岗位待办、准时率趋势等。

## 六、如何运行

```bash
# Windows（双击或在 cmd 里执行）
run.bat

# Git Bash / macOS / Linux
bash run.sh
```

脚本默认使用 IDEA 自带 JBR；换 JDK 时设置 `JAVA_BIN`：

```bash
set JAVA_BIN=C:\Program Files\Java\jdk-25\bin        # Windows cmd
export JAVA_BIN=/c/Program\ Files/Java/jdk-25/bin    # Git Bash
```

手动启动（等价命令，工作目录需为项目根）：

```bash
JAVAC="<jdk>/bin/javac"
JAVA="<jdk>/bin/java"
"$JAVAC" -J-Dfile.encoding=UTF-8 --add-modules jdk.httpserver -encoding UTF-8 \
  -d build/classes $(find src/main/java -name '*.java')
APP_DATA_DIR="$PWD/data" APP_WEB_DIR="$PWD/web" \
  "$JAVA" --add-modules jdk.httpserver -cp build/classes com.salesorder.App
```

| --------- | --------------------------------- |

| 环境变量 | 默认值 | 说明 |
| ------------------------------ | -------------- | -------------------- |
| `APP_PORT` | 8080 | 端口 |
| `APP_BIND_ADDRESS` | 127.0.0.1 | 绑定地址 |
| `APP_DATA_DIR` / `APP_WEB_DIR` | `data` / `web` | 数据与静态页目录 |

## 九、工程反思

- **状态机不是可选项**：业务流程一长，"状态随便跳"就会出现脏数据；把合法跳转收敛到一处，PC/手机端天然一致。
- **并行会签是效率杠杆**：把"全串行评审"改成"标准并行、非标定稿后并行"，是这套系统最大的提效点。
- **SLA 是兜底**：再好的流程也会有人离职、单据搁置，逾期自动升级给主管，系统才"活"起来。
- **零依赖不等于低质量**：基础设施（路由、鉴权、存储、状态机、流程引擎）自己写，反而把"系统由哪些零件组成"讲透了，也更利于迁移到 Spring Boot（`Router`→`@RestController`、`FlowEngine`/`StateMachine`/`BusinessRules` 原样保留）。
